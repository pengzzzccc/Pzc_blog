## **1. Decoupling Gameplay Simulation from Presentation via Event Buses**

In a fast-paced 2D platformer like **Bomb Slime**, a single bomb detonation triggers a cascade of side effects: chain-detonating nearby bombs, shattering breakable walls, applying knockback to zero-gravity floating bombs, shaking the camera, triggering hit-stop, playing 3D spatial audio, and firing adaptive-trigger haptics.

To prevent tight coupling between physics simulation and presentation systems across our **5-person team**, I architected **eight domain-specific static event buses**. Gameplay components only raise pure domain events, while dedicated presentation directors subscribe to them:

- **Visual Effects Director**: Listens to blast and impact events to dispatch screen shake, hit-stop, and camera zoom punches.
- **Spatial Audio Director**: Subscribes to hazard, item, life, player, and rope-gun buses, routing spatial sound cues through priority-based voice pooling compatible with both desktop and WebGL backends.
- **Haptics Director**: Translates gameplay events into gamepad rumble and DualSense adaptive trigger resistance.
- **Death and Respawn Directors**: Listen to player death and checkpoint events to execute cause-specific death presentations and restore level state.

## **2. Composable Interactable Framework and Checkpoint State Rewind**

Rather than relying on deep inheritance hierarchies for level objects, every hazard, pickup, and destructible in **Bomb Slime** is an interactable node assembled from orthogonal components:

- **Detonation Component**: Handles contact, hazard, armed-impact, and chain-reaction explosions.
- **Breakable Component**: Shatters terrain when caught within an active blast radius.
- **Carriable Component**: Allows the player to reel a bomb in with the rope gun, swallow it into inventory, and spit it back out armed.
- **Zero-Gravity Floating Component**: Enables eight-directional knockback from blasts or player contact for aerial puzzle chains.
- **Restorable Component**: Registers the entity with the room state manager for checkpoint rollback.

Because puzzles in **Bomb Slime** rely on consuming bombs and destroying walls, dying mid-room would leave a puzzle unsolvable if only the player respawned. I implemented a **memento-based checkpoint snapshot system** on the persistent game manager that captures the state of all restorable entities upon scene entry and checkpoint activation, rolling back the entire room cleanly on respawn. I also built an **automated geometry recovery solver** that detects when high-speed dashes or explosions wedge the player inside terrain colliders, nudging them to the nearest safe spot or returning them safely to the active checkpoint.

## **3. Data-Driven Playtesting and Offline Telemetry Suite**

To evaluate level pacing and identify frustrating choke points during playtesting, I built a complete offline telemetry pipeline:

- **In-Game Telemetry Recorder**: Records periodic player position and velocity samples alongside structured event rows for deaths, respawns, checkpoints, segment completions, and unstuck interventions, automatically stamped with the active Git branch and commit hash.
- **Standalone Web Analytics Viewer**: A zero-dependency static web dashboard where designers drag and drop telemetry logs onto exported level art to inspect death heatmaps, lethality contours, mechanic usage overlays, ghost replays, per-segment clear rates, respawn traps, and synchronised FPS, frame-time spike, and memory allocation charts.
- **Unity In-Editor Scene Overlay**: Renders the exact same death markers, heatmaps, and player trajectories directly inside the Unity Scene View so level designers can iterate on hazard placement in place.
